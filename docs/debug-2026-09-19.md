## CEC — current unresolved issue

CEC did **not** work in the PiTV launcher immediately after boot/update, before Kodi was launched. Therefore Kodi cannot be the original cause of the CEC failure.

Kernel/device state was confirmed healthy:

- `/dev/cec0` and `/dev/cec1` exist.
- Active connector is `/dev/cec0`.
- `/dev/cec0` physical address: `2.0.0.0`.
- PiTV registered as logical address 4 / Playback Device 1.
- `/dev/cec1` is disconnected (`f.f.f.f`).
- root CEC monitor was running:
  - `pitv-cec-monitor /dev/cec0 monitor`
  - `cec-ctl -d /dev/cec0 --monitor --show-raw`
- sudo rule for `pitv-cec-monitor` is present.

Manual command:

```bash
sudo -u pitv sudo -n /usr/local/libexec/pitv-cec-monitor /dev/cec0 active
```

successfully transmitted:

- `ACTIVE_SOURCE`
- physical address `2.0.0.0`

Later, after Kodi was forcibly terminated and PiTV launcher was visible again, the user confirmed that the TV remote worked.

### Important interpretation

Do **not** conclude that Kodi alone caused the CEC failure: CEC was already broken before Kodi launched.

The strongest current hypothesis is that PiTV registers the CEC playback logical address after boot/reconnect but does not reliably announce itself as the active source. Next session should test/fix this explicitly by sending `active` immediately after successful CEC `register`, and again after CEC/HDMI reconnect. Validate on the physical TV after a cold/reboot start.


This is expected to be investigated separately from the initial launcher CEC problem because PiTV currently owns the kernel CEC monitor. The intended design is one PiTV CEC owner with translated keys relayed to foreground apps.

After the boot/active-source issue is fixed, test whether PiTV CEC input is correctly relayed into Kodi.

## Kodi lifecycle — separate confirmed bug

During the physical test:

- launcher/wrapper process became `[kodi] <defunct>`
- actual `kodi.bin` continued running
- `kodi.bin` had been reparented to PID 1
- `SIGTERM` through `pkill -TERM -u pitv -x kodi.bin` did not stop it in that test
- force-killing the actual `kodi.bin` returned to the launcher

This shows PiTV cannot rely only on the short-lived shell/wrapper process for Kodi lifecycle tracking. The launcher must track the real Kodi process/session or use a wrapper that stays attached to the real process for the full lifetime.

This lifecycle bug is **separate** from the fact that CEC was already broken before Kodi launch.

## Missing kodi-send on physical base Kodi install

`sudo pitv-session-run kodi-send --action="Quit"` failed with:


The Store's Plex path can install `kodi-eventclients-kodi-send`, but a plain Kodi installation may not have it. If PiTV relies on `kodi-send` for general Kodi lifecycle/control, ensure it is installed together with Kodi or avoid requiring it for ordinary Kodi launch/quit.

## Late finding: stale Android Stremio + missing per-app uninstall

After the main checkpoint, the user tested Stremio and the system became unresponsive/stuttered again. The UI appeared to expose an older Android Stremio installation that should no longer be the preferred PiTV Stremio path.

Current repository intent is **native Linux ARM64 Stremio via system Flatpak**:
- Store item `stremio` uses `type: flatpak`
- app id: `com.stremio.Stremio`
- launcher command: `flatpak run com.stremio.Stremio`

Therefore any Android Stremio shown on the physical device is legacy persistent data from an older PiTV build, not the current Store definition.

Why it can survive updates:
- PiTV intentionally preserves `/var/lib/pitv/apks`, `/home/pitv/PiTV/APKs`, Waydroid data, and user config.
- `discover_apks()` automatically surfaces every APK found in the preserved APK folders.
- A legacy APK can therefore remain visible even after the Store catalog migrated Stremio from Android to native Linux.

Confirmed UI gap:
- Settings → Applications currently only supports **show/hide** for installed app entries.
- Android/APK rows can refresh and launch APKs but have **no uninstall/delete action**.
- PiTV Store treats an installed item as a launch action; there is **no per-app uninstall flow**.
- So the user is correct: PiTV currently lacks a real application removal UI.

Next-session requirement:
1. Identify the legacy Stremio APK/package on the physical device before deleting anything.
2. Remove the stale Android Stremio APK + Waydroid package + stale Store receipt if applicable.
3. Add a real **Uninstall / Remove** action with confirmation.
4. Handle each install type safely:
   - Flatpak: system `flatpak uninstall`
   - Android APK / Play Store: Waydroid package uninstall
   - PiTV-downloaded APK: also delete managed APK file and receipt
   - APT app: restricted allowlisted apt remove, only where PiTV owns the package
   - Kodi add-on: remove the specific PiTV-managed add-on, not Kodi itself unless explicitly requested
5. After uninstall, refresh launcher/Store state and remove obsolete hidden-app entries.
6. Add migration/cleanup logic so obsolete Android Stremio from old PiTV builds does not reappear once native Linux Stremio is the supported path.

Do not blindly delete unknown Android packages; inspect the physical device first.


## Late finding: CEC recovery was only temporary

The user reports that the TV remote worked only briefly and then stopped responding again.

This weakens any conclusion that a single manual `ACTIVE_SOURCE` transmission permanently fixes the problem. The manual `active` command can restore control temporarily, but the failure returns.

Implications for next session:
- Do not treat `ACTIVE_SOURCE` alone as the final fix.
- Capture CEC monitor output while the remote is working and again immediately after it stops.
- Verify whether the long-running `cec-ctl --monitor --show-raw` process is still alive when input stops.
- Verify whether `/dev/cec0` still has logical address 4 and physical address 2.0.0.0 when input stops.
- Check whether launching/exiting external apps (Kodi/Stremio/Waydroid) changes active-source state or CEC logical-address registration.
- Consider a self-healing CEC state machine: register + active on startup/reconnect, detect lost input/adapter state, and re-register/re-announce only when needed rather than continuously.
- Preserve the existing one-owner design; do not let Kodi/libCEC and PiTV kernel CEC monitor fight over the adapter.
