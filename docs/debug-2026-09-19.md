## Upstream Waydroid source comparison — fullscreen fix

Compared PiTV against current upstream `waydroid/waydroid`, official Waydroid docs, Cage, labwc, and Raspberry Pi-specific Waydroid guidance.

Confirmed mismatches found:
- Upstream marks `waydroid shell` as a **root-only** CLI action. PiTV's CEC relay previously executed `waydroid shell input keyevent ...` directly as the unprivileged `pitv` GUI user. This is a real bug and explains unreliable/non-working DPAD relay into Android.
- PiTV previously started `waydroid session start` itself and then called `waydroid app launch`. Upstream `app_manager` is designed to start the session itself when needed; its app-launch path uses a foreground session (`background_start=false`).
- Official fullscreen docs use `waydroid show-full-ui`; official Waydroid-only/kiosk docs explicitly show `cage waydroid show-full-ui`.
- PiTV never explicitly controlled `persist.waydroid.multi_windows`. Because Waydroid data survives PiTV updates, an old `multi_windows=true` value could silently persist across versions.
- Raspberry Pi guidance requires a 4 KiB page-size kernel and PSI; PiTV previously did not validate either before launching Android.

PiTV 1.4.22 changes:
- Android is isolated in a nested Cage kiosk compositor rather than mapped directly into the main labwc compositor.
- Cage launches the official `waydroid show-full-ui` path; once ready, PiTV forces `persist.waydroid.multi_windows=false` and launches the selected Android package inside that fullscreen session.
- stale Waydroid user sessions are stopped before Cage starts so Android binds to Cage's Wayland socket instead of reusing the old labwc-bound socket.
- labwc maximizes the nested wlroots/Cage surface.
- CEC Android key relay now uses a narrowly allowlisted root helper for keycodes 4/19/20/21/22/23/85.
- Android launch preflight checks 4096-byte pages and `/proc/pressure`.

Important nuance:
- Some Raspberry Pi desktop guides set `multi_windows=true` as a workaround for compositor black-screen problems. PiTV 1.4.22 intentionally does not use that desktop integration path: Android runs in a dedicated Cage fullscreen surface, matching Waydroid's kiosk/fullscreen documentation.


## Upstream Waydroid comparison — concrete PiTV fixes

Review against current upstream Waydroid code found two important integration differences:

1. **Android key relay was wrong in PiTV.**
   Upstream marks `waydroid shell` as a root-only CLI action. PiTV previously tried to relay CEC/DPAD with `waydroid shell input keyevent ...` directly from the unprivileged `pitv` GUI user, so Android navigation could silently fail while PiTV still consumed the TV's CEC keypresses. PiTV now routes only an allowlisted set of Android TV keycodes through the restricted root helper action `waydroid-keyevent`.

2. **Waydroid is now bound to a dedicated fullscreen compositor.**
   Upstream `show-full-ui` starts the Waydroid session when no user session exists and binds that session to the current `WAYLAND_DISPLAY`. PiTV therefore stops any stale Waydroid session first, launches nested Cage, then runs `waydroid show-full-ui` inside Cage so the Android session binds to Cage instead of directly to the PiTV/labwc socket. The persistent property `persist.waydroid.multi_windows` is forced to `false` before the selected TV app is launched.

Additional Raspberry Pi checks were added for a 4 KiB page-size kernel and PSI availability (`/proc/pressure`). Binder setup remains delegated to Waydroid's own driver helper rather than duplicated in PiTV.

The nested Cage Wayland backend exposes its parent toplevel with the standard wlroots app-id, and PiTV's labwc rule maximizes that surface. Because PiTV has no desktop panel/gap, this gives the Android kiosk the full TV canvas while keeping the main PiTV compositor isolated underneath.
